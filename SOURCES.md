# SOURCES

Every dataset, fare table and reference used by JourneyMind, and — just as
importantly — what is **not** real. The project documentation asks for one row
per source with a URL, a date, a licence and what it is used for. This is that
file, and it is the file to update first when anything changes.

**Date of this record: 2026-08-27.** Portals move, feeds break and licences
change. Nothing here should be cited as evidence that a feed is live today;
verify before building on it.

---

## 0. Two bundles, and which one you are looking at

There are now two study-area bundles, and they differ in exactly one thing:
where the network came from.

| | `bengaluru_south` (default) | `bengaluru_osm` |
|---|---|---|
| Road network | **synthetic**, `scripts/generate_dataset.py` | **real**, OpenStreetMap via Overpass |
| Junctions / road edges | 224 / 527 | 1,398 / 1,440 |
| Bus stops | invented positions | **real**, OSM `highway=bus_stop` |
| Bus routes | invented stopping patterns | **real**, 14 BMTC relations of the 244 in the corridor |
| Metro stations and lines | real names, approximate positions | **real**, OSM `route=subway` relations, cited by id |
| Place coordinates | typed in by hand | **real**, Nominatim |
| Travel-time observations | simulated | **simulated** |
| Ride-hailing fares / availability / cancellation | modelled | **modelled** |

Select one with `JM_CITY=bengaluru_osm JM_MODELS_DIR=models_osm`. The default
stays synthetic so the bundled demo runs with no network and no surprises.

**The bottom row is the one that matters.** Even in the OSM bundle the model's
training TARGET is generated, because no free source publishes per-edge
observed travel times for Bengaluru — the APIs that carry them are commercial
and keyed, and scraping one would breach its terms. What the OSM bundle buys is
that the simulation runs over a **real topology**: real road classes, real
distances, real speed limits where OSM has them, real station order. That is a
materially different claim from "invented ground", and it is the only claim
made for it.

### How it was built

```
python scripts/fetch_osm.py         # Overpass + Nominatim -> the real network
python scripts/build_osm_bundle.py  # city record, fares, generated observations
JM_CITY=bengaluru_osm python scripts/train.py --all --out-dir models_osm
```

Both fetchers cache to `data/_osm_cache/`, so a re-run costs the donated
infrastructure nothing. Overpass gets exponential backoff on 429 and a real
User-Agent; Nominatim gets at most one request per second, as it asks.

## 1. What is real, and what is not

This is the single most important section in the file.

| Element | Status | Detail |
|---|---|---|
| Metro station names, line assignment, approximate coordinates | **Real, public** | The publicly documented Namma Metro network (Purple, Green and Yellow lines), as also mapped in OpenStreetMap. The Yellow Line is truncated at Bommanahalli because the study bbox ends there; in reality it continues to Bommasandra. |
| Metro / bus first and last service times | **Real, approximate** | Published first- and last-service practice (metro ~05:00–23:30, later start at weekends; buses ~05:30–23:00), rounded to the half hour. Not a timetable — no individual departure is scheduled. |
| Named places (Wipro Doddakannelli, PES University RR campus, and the rest) | **Real, approximate** | Real addresses inside the corridor, positioned to roughly their published coordinates. Positions are good to a street, not to a doorway. |
| Metro fare structure | **Real, transcribed** | BMRCL distance-slab table, transcribed by hand. Verify before quoting. |
| Bus fare structure | **Real, transcribed, approximated** | BMTC ordinary-service stage fares, approximated as distance slabs. |
| Auto-rickshaw meter rate | **Real, transcribed** | Karnataka RTO regulated rate. Presented as an estimate because what is charged often differs from the meter. |
| Road junctions and the road graph | **SYNTHETIC** | Generated by `scripts/generate_dataset.py`. Not an OSM extract. |
| Bus stop positions, routes, headways | **SYNTHETIC** | Plausible arterial alignments, invented stopping patterns. |
| **All travel-time observations** | **SYNTHETIC** | Generated. No real trip was ever logged for this repository. |
| Ride-hailing fares (Rapido, cab, Namma Yatri) | **MODELLED ESTIMATE** | `base + per-km + per-min`, with an uncertainty band. Never a quote. |
| Surge pricing | **NOT MODELLED** | Proprietary and unpredictable without operator data. Deliberately absent. |
| Real-time traffic | **NOT USED** | There is no live traffic source in this project. What the interface calls "live" is the *current clock* driving the model's time-of-day features and the service-hours check — not a live feed of anything. |
| Real-time vehicle positions / availability | **NOT USED** | No GTFS-Realtime feed is consumed. |
| Geocoding a typed place name | **LIVE, at request time** | When a rider types a name that is not one of the bundled fifteen, that name — and nothing else from the request — is sent to Nominatim, bounded to the study bbox. Cached to disk, one request per second, 4-second timeout, and it falls back to the bundled list on any failure. `JM_GEOCODER=0` disables it and the build makes no outbound call at all. |

The application labels this in the interface as **"Demo / estimated data"** and
tags every individual number with its provenance (`published`, `estimated`,
`predicted`). That labelling is a product requirement, not decoration.

## 3. Sources considered and deliberately NOT used

Listed so that the decisions are visible rather than implicit.

| Source | Status | Why not |
|---|---|---|
| **Uber / Rapido / Namma Yatri / Ola app endpoints** | **Closed — never touched** | These are products, not data sources. Their private endpoints are protected by terms of service. Reverse-engineering them is not OSINT and is not done here. |
| **Commercial routing APIs** (Google Maps Platform, Mapbox, HERE, TomTom) | Not used | Terms typically forbid storing results or using them to train a competing model. Using one as an *evaluation reference* would be legitimate; this project has no budget line for it and makes no claim against one. |
| **Uber Movement** | Not used | Availability has not been reliable in recent years. Not assumed accessible. |
| **BMTC / BMRCL GTFS (Enroute Mobility-as-a-Service release)** | Not used **in this build** | A real GTFS feed is the correct next step and the data layer is built for it (see §5). Access route and current publication point were not confirmed, and the project's hard rule is that the MVP may not depend on an unconfirmed feed. |
| **Delhi OTD GTFS + GTFS-Realtime** | Not used | Different city. Listed because it is the strongest open Indian transit feed and the obvious target for a second study area. |
| **GTFS-Realtime archives** | Not used | No feed is being archived by this project. Consequently there are no real observed run-times, which is exactly why the travel-time data is synthetic. |
| **Census of India 2011 journey-to-work tables** | Not used | Needed for the accessibility-atlas extension (Part 3 of the documentation), which is out of scope for this MVP. |
| **METR-LA / PEMS-BAY** | Not used | Californian road-speed benchmarks. Methodologically useful for validating a GNN pipeline against the literature, and a reasonable future step, but not Indian data. |

## 4. The honesty note about the training data

The bundled travel-time observations are generated by a model with a known
structure. In that generator, an edge's delay depends on the **neighbourhood
mean** of a latent per-node congestion field, while node features expose only a
**noisy** per-node reading of it. That design makes neighbourhood averaging
useful *by construction*.

Two consequences, both of which must be stated wherever numbers from this
project are quoted:

1. **Any GraphSAGE-versus-MLP result measured on this bundle is a statement
   about this generator, not about Bengaluru.** It cannot support a claim that
   graph structure helps travel-time prediction in a real city.
2. **The absolute error figures are not research-grade.** They describe how well
   a model recovers a process we ourselves wrote down.

What the synthetic data *is* good for: proving that the whole pipeline runs
end to end, that the training and serving paths agree, that the temporal split
is honest, and that the comparison harness works — so that the moment real
logged trips exist, the experiment is one command away.

`EVALUATION.md` reports the measured numbers, including the ones that are
unflattering.

## 5. Swapping in real data

The data layer exists so this is a small change, not a rewrite. Implement
`TransportDataProvider` (`backend/app/data/provider.py`):

```python
class TransportDataProvider(ABC):
    def get_city(self) -> CityMeta: ...
    def get_nodes(self) -> Sequence[Node]: ...
    def get_road_edges(self) -> Sequence[RoadEdge]: ...
    def get_transit_edges(self) -> Sequence[TransitEdge]: ...
    def get_transfer_edges(self) -> Sequence[TransferEdge]: ...
    def get_transit_routes(self) -> Sequence[TransitRoute]: ...
    def get_fares(self) -> dict[str, FareModel]: ...
    def get_travel_times(self) -> Iterable[TravelTimeObservation]: ...
    def get_places(self) -> Sequence[Place]: ...
```

Then change the one line in `get_provider()` in
`backend/app/data/static_provider.py`. Nothing in the graph, model, routing or
optimisation layers refers to a file path.

The minimum viable real stack, per the project documentation:

1. An OSM extract for the study area (Geofabrik → OSMnx) for the road and
   footpath network.
2. One GTFS feed, clearly labelled official or community.
3. Published fare tables — already here, and the least likely to break.
4. **Your own logged trips**, six to eight weeks on a defined corridor. This is
   the item that actually unblocks the research question, and the one most
   often left until too late.

## 6. Licensing and ethics rules this project follows

- **OSM attribution is displayed**, in the application, on every map.
- **No private app endpoint is queried**, scraped, or reverse-engineered.
- **No paid API is laundered**: no commercial routing result is stored,
  redistributed, or used as a training label anywhere in this repository.
- **No personal data is collected or stored.** There are no accounts, no
  cookies, no tracking, and no trip history. The recommendation endpoint is
  stateless; the only thing retained in memory is a per-IP request counter for
  rate limiting, which expires after 60 seconds.
- **Every estimate is labelled an estimate** in the interface, at the level of
  the individual number rather than in a footnote.
